## 筛选语义（Filter Semantics）

| 抽象 | 位置 | 用途 |
|-------------|----------|---------|
| useFilterStore | stores/filter-store.ts | 屏幕（顶栏，top-bar）筛选：`filters`（一个 `FilterCriteria`）、`setShowCompleted` / `setPersonIds` / `setStatusIds` / `setSearchText` / `setDateRange`（将日期包装为固定锚点）/ `setTags`（通过 `assignedTagsMap` 实现 OR 语义）、`setAllFilters` / `clearAll`，以及派生的 `isActive`（`countActiveFilters > 0`）。由 TopBar 的 `FilterChipBar` / 移动端 `FilterSheet` 编辑；`App.tsx` 在每次 pathname 变化时清空它。criteria 类型、转换器与求值器都是 `utils/` 中的纯模块。`setNegated(field, on)` 在“是”（is）与“不是”（is not）之间切换某个字段并保留其已勾选项；每次写入都会被规范化（一个没有勾选任何项的"is not"等于没有筛选，该开关随字段一起丢弃；各 setter 保留字段的开关）；`clearAll` 丢弃所有开关。 |
| FilterCriteria, fixedAnchor, countActiveFilters, composeScreenFilter, criteriaToPredicate / predicateToCriteria | utils/filter-criteria.ts | `FilterCriteria`：personIds、statusIds、tags 为 null\|Set 形式的数字 id；showCompleted、searchText、dates（`DateFilters`：每种日期类型一个子句——`deadline` = 到期日 / `followup` = 下次跟进 / `created` / `modified`——每个都是一段 `DateAnchor` 区间（在到期日 / 跟进上带 `includeNoDate`），以及“有日期”（Has a date）或“无日期”（No date）；每个子句都必须通过，`utils/filter-match.matchesDateMatch`；屏幕筛选的 `setDateRange` 设置的是到期日区间），markers——优先级（Priority）筛选（`MarkersFilter \| null`：`'hot'` = 按 `settings.hotRule` 判定为 hot，或要求每个 marker 为“是”（Yes，`true`，必须有）/ “否”（No，`false`，必须没有），Urgent = 相对 `settings.urgentDueWithinDays` 的实际紧急；`utils/markers.matchesMarkers`）。`countActiveFilters`——每个控件计一（人员、状态、标签、日期——无论筛了多少种类型都只计一次——、markers、显示已完成、搜索）；驱动移动端的“筛选”（Filters）徽标。`composeScreenFilter(screen, list)`——任务必须同时通过的两个阶段：收窄子句按 AND 严格求交（即便在同一字段上——屏幕 `@Alice` + 列表 `@Bob` = 同时分配给两者的任务），`showCompleted` 以 OR 并入两者。运行时 `FilterCriteria`（Set）与可序列化 `TodoPredicate`（数组）之间的转换器；`predicateToCriteria` 通过 `utils/date-filters.readDateFilters` 读取日期子句（锚点经 `readDateAnchor` 读取；筛不出任何内容的子句会被省略），仅从数组构建 id Set（其他任何值 = 无筛选），并规范化 markers（`{}` → null）。可选的 `negate`——人员 / 状态 / 标签的"is not"开关（`utils/filter-negation`）；组合时保留各自一侧的开关（屏幕 Status is not Waiting AND 列表 Status is Waiting，Done → Done）。 |
| FilterSettings, matchesFilter / matchesFilterWithLookups / applyFilter / createPredicateEvaluator / matchesComposedFilter / createScreenComposedEvaluator | utils/filter-match.ts | 各求值器——纯函数：每一个都接收 `FilterSettings`（`MarkerSettings` + `weekStartsOn`，来自 `useFilterSettings` 或 `settings-store.currentFilterSettings`）和 `today`。`matchesFilter(filters, todo, personIds, today, searchCtx, tagIds, settings)` 是核心：人员筛选就是对 todo 已分配人员做简单的集合成员判断（`0` = 未分配哨兵值）；状态本身绝不会隐藏任务；`today` 和 `settings.weekStartsOn` 解析相对日期区间记号；非空的标签子句会排除没有任何标签分配的任务。`matchesFilterWithLookups` 从 `TodoNameLookups` 解析人员 / 标签 id 和搜索上下文（`utils/filter.textMatchContextFor`）——它是 `applyFilter`（日历、Eisenhower、仪表盘）和 `createPredicateEvaluator(lookups, today, settings)`（列表小部件针对已存储 `TodoPredicate` 的 `evalPredicate`；每个谓词只转换为 criteria 一次）背后共同的唯一路径，因此搜索在所有界面上都能命中人员 / 状态 / 标签名称。`createScreenComposedEvaluator(screen, lookups, today, settings)` 是列表小部件传给 `buildList` 的那个 `evalPredicate`（经 `composeScreenFilter`） |

| 抽象 | 位置 | 用途 |

| makeEnsureLoaded | stores/store-helpers.ts | `makeEnsureLoaded(load, isLoaded)` → 一个 `ensureLoaded()`，调用方可以在每次挂载时触发它而不会重复访问 IndexedDB。并发的调用方共享进行中的加载；一旦 `isLoaded()`——即 store 的 `loaded` 标志，只由一次读取成功的加载设置——为 true，调用就是空操作。一次失败的加载（由 `loadFresh` 上报）会让标志保持 false，因此下一次 `ensureLoaded()` 会重新读取；promise 永不拒绝。该标志是 store 状态，因此随 store 一起重置。由 `useTodoStore.ensureAllLoaded`、`usePersonStore.ensureLoaded`、`useStatusStore.ensureLoaded`、`useTagStore.ensureLoaded`、`useListDefinitionStore.ensureLoaded` 使用（`useListOrderStore.ensureLoaded` 在它自己的 `loaded` 上遵循同样的规则）。恢复 / 导入通过 `refreshAllStores` 重新加载，后者直接调用每个 `load()`。进行中的加载是模块状态：`resetModuleState`（测试）会忘记它，而被忘记的加载完成时绝不会清除它的后继者 |
| trackWrite, readFresh | stores/store-helpers.ts | 防止 `load()` 在其读取进行期间把一次编辑已经更改过的行放回去。每次 store 写入（状态更改 + 数据库写入）都经过 `trackWrite`——`mutate` / `optimistic` 为它们的调用方做到这一点；todo / person / tag / status / list / list-order / settings store 的其余写入则自行包装。加载通过 `readFresh` 读取：它先等待没有受跟踪的写入在进行中，然后读取，如果期间有写入开始就再次读取（在 5 次读取后放弃并发出警告）。只有一个全应用范围的跟踪器，因此例如一次 todo 加载也会等待一个清除 `statusId` 的 status 删除。规则：受跟踪的写入绝不等待 `readFresh` 加载（死锁）；`loadAssignments` 不使用它（它改为与最新映射合并），因此写入可以调用它。未覆盖：workspace store（`init` / `load(id)` 打开一个布局——不可能有编辑待处理）和 note store（其加载在启动时 / 导入后运行；正在输入的笔记以防抖方式保存）。`resetWriteTracking` 是共享 vitest setup 的文件边界重置 |
| loadFresh, reportLoadFailure | stores/store-helpers.ts | store 加载的 `readFresh` 读取；失败时返回 undefined。`reportLoadFailure(label, error)` 记录一次失败的加载，并把 `Couldn't load <label>. | mutate | stores/store-helpers.ts | store 变更动作的受跟踪包装器：记录失败并重新抛出 |
| optimistic | stores/store-helpers.ts | 受跟踪的乐观更新变更：同步应用状态，异步持久化，失败时回滚；撤销只在持久化成功之后才注册。回滚是**条目级**的：每个调用方只放回它自己的写入所更改的内容（该任务的字段、那一个 person / tag / status / list——且仅当它仍然持有这次编辑时——、它添加或移除的指派条目，位于它们原来的位置），因此期间已落地的并发编辑保留其值 |
